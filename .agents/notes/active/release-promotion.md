# 预发布验证后晋升正式版

## 用户原始要求

> 后续打tag发布先打alpha或者beta，成功后再切成正式 以免错误的发布占用版本号，这条写进项目规格

## 发布约束

- 每次发布先使用目标版本的 alpha 或 beta 标签，例如 `v2.0.3-beta.1`，禁止直接推送尚未验证的正式标签 `v2.0.3`。
- 预发布使用匹配的应用版本和带明确日期的中英文更新日志；GitHub Release 必须标记为 prerelease，不进入正式版更新提示。
- 只有预发布工作流全部成功，Windows、macOS、Linux 安装包均已实际发布且非空，才允许晋升正式版。失败则修复后递增预发布序号，例如 `v2.0.3-beta.2`，继续验证，保留正式版本号。
- 晋升时将应用版本和中英文日志更新为正式版本，创建新的正式标签；保留原预发布标签，不重命名或移动已经公开的标签。
- 正式版代码必须与通过验证的预发布一致，仅允许版本号、发布标识和更新日志等发布元数据变化。功能、依赖或构建逻辑变化必须重新经过预发布验证。
- 正式标签仍须执行完整发布工作流，并验证三平台安装包、正式 Release 标记和最新正式版更新入口。预发布成功不等于正式版已经发布。
- 按 `AGENTS.md` 的 Release Completion 要求部署对应网站日志，并验证线上中英文页面；任何构建或部署失败都必须如实报告。

## 验收与禁止方案

- 正式标签推送前，必须有同版本已成功发布的 alpha 或 beta 记录及三平台安装包证据。
- 参见 [禁止直接用正式标签试构建](../prohibited/unverified-stable-release-tag.md)。
